# PR 作成とレビュー

依頼された変更をコミットして PR を作り、最新コミットの CI 結果を含めて Terra（low）にレビューさせる。マージは行わない。

## コミットと PR 作成

1. リポジトリの `AGENTS.md`、現在ブランチ、作業ツリー、base との差分を確認する。既定ブランチ上なら作業ブランチを作る。無関係な変更はコミットに含めない。
2. 未コミットの対象差分があれば、必要なローカル検証を実施してコミットする。差分がなければ空コミットは作らない。
3. ブランチを push する。base は依頼とブランチの派生元を確認して選ぶ。現在ブランチの PR が既にあれば再利用し、その base が選定した base と異なる場合は合わせる。PR がなければ作成する。
4. タイトルと本文は日本語にし、最終差分の問題と変更後の振る舞いを説明する。`gh pr` と `gh api` はシェルで包まず直接呼ぶ。複数行の本文は一時 Markdown ファイルへ書き、`gh pr create --body-file <path> --assignee @me` で渡す。
5. 依頼やブランチ・コミットの情報から対象の GitHub Issue 番号を特定できる場合は、本文に `- Closes #<Issue番号>` を箇条書きで追加する。Linear の課題 ID や番号は GitHub Issue として扱わず、GitHub Issue との対応が確認できない場合は追加しない。

## PR 本文の検証欄

PR 作成前に `.github/workflows/` と呼び出されるスクリプトを読み、CI が実行する検証を特定する。ローカルで同じコマンドを実行していても、CI と重複する項目は本文の「検証」に列挙しない。ローカル検証の実施自体はリポジトリの指示に従う。

「検証」には実施済みの手動操作、表示確認、CI が扱わない追加チェックなどだけを書く。追加検証がなければ欄ごと省く。CI の通過コマンド一覧を別の見出しに移して重複を残すことも避ける。CI の結果はレビューへの引き継ぎと最終報告に含める。

## CI の完了待ち

1. PR の URL、base、head と最新 head SHA を取得する。
2. `gh pr checks <PR> --json name,bucket,link` で状態を確認する。実行中なら `gh pr checks <PR> --watch` で完了まで待つ。コマンドはバックグラウンド実行や短いツール待機で監視し、長時間ユーザーへの進捗報告を止めない。
3. watch 終了後に結果を再取得する。終了コードだけで成功と判断せず、失敗・キャンセル・スキップを区別する。チェックが未登録ならワークフローの起動状況を確認して再取得する。パス条件などで CI が実行されない場合はその理由を記録し、通過とは扱わない。
4. 失敗があれば `gh run view <run-id> --log-failed` などでログを取得する。依頼範囲の不具合は修正・検証・コミット・push して最新 head の CI を待ち直す。権限や外部サービスなどで解消できない場合は、原因と残る失敗をレビューにも渡す。

## Terra low のレビュー

CI 結果が確定したら、新しいサブエージェントを次の指定で起動する。このスキルの実行にはこのレビュー依頼を含む。

- `model: gpt-6.1-terra`
- `reasoning_effort: low`
- `fork_turns: none`

PR URL、リポジトリの作業ディレクトリ、base/head と head SHA、最新差分、適用されるルール、CI の各チェック結果とリンク、失敗ログや未実行理由、CI 外の検証結果を渡す。実装者の結論に依存せず差分と関連コードを読み、参照先・挙動・回帰・ルールの整合を確認するよう依頼する。指摘には重要度、ファイルと行、根拠を求め、問題がなければ明記させる。レビュー担当にはファイルの変更や GitHub への投稿をさせない。

親エージェントが指摘の妥当性を確認し、妥当なものを修正・検証・コミット・push する。更新後は CI を待ち直し、最新 SHA と結果を渡して再レビューさせる。同じ問題が修正後も2回続く場合や外部要因で進められない場合は、理由と未解決事項を報告し、無限に繰り返さない。モデルが利用できなければ黙って代替せず、その制約を報告する。

最後に PR URL、CI 結果、Terra low のレビュー結果、未解決事項を簡潔に報告する。CI 結果とレビューが最新 head に対応していることを確認する。
